# Shared billing dispatch budget — disabled L3-B1 source

B1 builds on the accepted L3-A composition `7b6936428852f0c3b79fbc9099ff58a7208c6932`. It supplies one physical-dispatch ledger for foreground billing, the existing L2 event processor and the injected L3-A reconciliation processor. It adds no trigger, pump, void endpoint, mobile behavior, provider activation, credit policy or retention decision.

## Construction and closed defaults

The real foreground and event factories use `createBillingRuntime`. `PLAY_BILLING_DISPATCH_CONFIG` is non-secret JSON with an exact `enabled`, 32-hex `epoch`, `global`, `sources` and `digest` shape. Dimensions are GET, ACK and KMS; sources are foreground, event and reconciliation. The digest is computed from the canonical fixed-order configuration. There is no source-supplied production allocation. Missing, malformed, disabled or all-zero configuration constructs disabled providers without GoogleAuth. Partial zero dimensions deny those dispatches. Provider-bearing construction reads the paired common controls and the legacy L2 controls under the original invocation deadline before constructing any provider dependency.

Prepare, disclosure acceptance and disclosure revocation explicitly use the safety-only construction path. That path does **zero budget reads**, even if the budget store never returns. Internal retirement remains a repository operation. Core identity, lifecycle and disclosure validation still apply. Local archive behavior is unchanged. An unavailable provider budget does not itself revoke an existing grant.

The event handler creates its existing 55-second ingress or 50-second pump deadline before configuration and construction. The same deadline reaches initialization reads, service work and cleanup. The foreground deadline includes identity verification elapsed time. Neither factory grants a new time allowance after authentication. Disabled ingress rejects with a fixed outcome for redelivery; a disabled pump does no work. Approved event key versions remain empty, so production event activation remains closed.

## Durable paired controls and legacy continuity

`playBillingDispatchControl/{marker,budget}` is server-only, has no TTL and never initializes itself. Both records bind schema, fixed project `my-art-collections`, package `app.archivale`, named database `archivale-play-billing`, epoch, configuration digest, cutover receipt digest and equal revision. Missing either record, malformed values, incompatible configuration, lost high-water or a backward clock fails closed. An empty store is not proof of a new installation.

The budget retains cumulative post-cutover totals for all three sources and all four actions (`play_get`, `play_ack`, `kms_encrypt`, `kms_decrypt`). GET, ACK and KMS starts retain a 15-minute rolling window; exact-boundary entries remain until strictly outside the window. Hard storage bounds are 120 GET starts, 30 ACK starts, 60 KMS starts, and 64 KiB per common record. Source caps are additional limits no greater than the common cap. Counters and their sums use safe integers; future or unsorted timestamps, impossible totals, overflow and unknown fields are unsafe. Failed, canceled, timed-out and uncertain calls retain their charge. No refund path exists.

The immutable legacy cutover floor stores either verified-new status or the retained L2 budget digest/revision/per-kind totals. A mutable `legacyHead:{revision,digest}` additionally binds the exact **current** legacy budget. Its digest canonically sorts map keys and serializes dates; Firestore map ordering cannot change it. Every event reservation atomically advances this head with the old L2 budget and the common reservation. Common and legacy circuit changes also advance their paired history together. All provider sources validate the live head, retained floors and minimum post-cutover event totals, and honor an old L2 open circuit. This rejects partial rollback of later totals or rolling entries, not only loss below the cutover floor. Old L2 discovery and job limits remain extra subcaps; they are not another project allowance.

This ledger cannot detect a coherent administrative rollback of all mutually consistent controls and associated source records, nor account for unrelated clients sharing Play/KMS authority. Backups, operator recovery and uncontrolled external traffic remain activation dependencies. It is not a provider-side spending limit or a lossless total-outage guarantee.

## Atomic local reservations and single-use tickets

The repository composes local and common writes in one transaction, reading every preimage before writing. A local or common denial writes neither physical ledger. Existing account/token admissions, inbox capacity, attempt history and ACK intent remain intact.

A new account observation gets paired `billing-local-dispatch-v1` counters capped at 3 GET, 1 ACK and 3 KMS calls. Old owners without the pair cannot dispatch; a bounded predecessor continuation retains its counters. Event rows retain cumulative totals and add a paired version/base snapshot only on a genuine new owner. Same-owner retries never reset that base. Reconciliation retains its cumulative work counters and uses the admitted account owner limits. Event account dispatch charges the owner, event row, legacy aggregate and common controls atomically. Reconciliation charges owner/work/common; foreground charges owner/common; inbox/discovery charges event/legacy/common.

Internal capabilities are a closed union: selected account attempt; exact competing-current decrypt/GET; reserving inbox encryption; working inbox decrypt/discovery GET. They carry opaque fingerprints and immutable owner/phase/index/epoch/assertion/work snapshots. They contain no raw UID, purchase token, ciphertext, plaintext or auth headers. Completed reconciliation response receipts cannot reserve work. Auxiliary-current capabilities confer no ACK, encryption, promotion or arbitrary token access. Source is derived from durable account/work state.

Actual Google Play and KMS transports require an injected gate, including direct construction. Custody forwards the same capability with purpose-separated, version-bound AAD. The transport captures URL and serialized body before reservation/authentication. Descriptor binding includes target token HMAC, action, product/ACK body or KMS resource/version/AAD/body digests. Decrypt binds the retained envelope. The same captured bytes reach fetch after delayed authentication; caller mutation cannot replace them.

A successful committed reservation creates a process-local random single-use ticket. Ticket payload uses frozen plain primitives; nonces are hex strings and expiries are numbers. Private state and cancellation signal are outside the payload. No ticket is persisted or accepted from a client. Unknown transaction outcome yields no usable ticket; a possibly committed charge stays retained.

Before fetch, the ticket moves synchronously from fresh to checking. A read-only transaction validates the original owner/phase/index, disclosure, lifecycle, real work fence, common epoch/configuration and closed circuits. It permits unrelated later common revisions but requires a revision at least that of the reservation. The fresh clock is read after all asynchronous database reads. Ticket expiry is capped by the original invocation, the existing 10-second transport limit and every required captured owner/work lease and consent expiry. A later extension cannot renew an old ticket. Immediately before fetch, the original cancellation signal and captured/final expiry ceilings are checked again with no intervening await. Ticket success, failure and synchronous fetch exceptions all spend the ticket.

The repository check and external fetch are not one atomic system. Already-dispatched work and already-emitted responses cannot be recalled. Server publication/final-response fences remain in force; the existing mobile memory lease and delayed-response limitations are unchanged. No stronger immediate-revocation promise is made.

## ACK and configuration failures

ACK intent still commits before physical reservation. If a later budget/auth check denies the ACK, no request is sent, but the conservative acknowledgement-unknown barrier and cooldown remain. Recovery requires a new authoritative GET. An acknowledged response avoids another ACK; a still-pending purchase needs a separately charged ACK. HTTP409 remains a transient conflict, with no blind inline retry.

Authentication classification inspects only structured status/code at getClient/header acquisition. Known transient HTTP/network codes stay transient. Deterministic auth configuration failures, invalid client/header shape, and otherwise unclassified pre-fetch auth exceptions become fixed configuration-unavailable outcomes. No provider error message, credential path, header or payload is inspected or logged. This conservative choice can stop traffic after an unstructured transient auth error and is an explicit availability tradeoff. Reservation denials are not auth errors. Unknown post-auth fetch failures remain transient; 404/410 never by themselves revoke entitlement.

Configuration failures poison the current gate and attempt to open common/legacy circuits transactionally, preserving totals and using the existing transport deadline/cancellation for cleanup. Persistence failure does not permit another request through that gate. There is no runtime auto-close, reset or repair endpoint. A separately authorized operator CAS/readback must preserve epoch, totals and history.

## Activation and test boundaries

B1 implements only pure initial-record proposals, never a database initializer. Activation requires separately approved global/source allocations, runtime/cost ownership, circuit repair procedure, exact project/database/configuration readback and a verified cutover. Stop and drain all incompatible dispatchers; inventory other users of the same provider authority; retain old L2 controls/work and their exact historical preimage. A genuinely new state requires authoritative emptiness evidence; no-payments attestation is insufficient. Require at least 16 minutes after the last possible old invocation admission, confirmed drain and no uncontrolled writer before proposing an empty common rolling window. The bound covers the old 55-second invocation plus 15-minute window. Ambiguous history blocks activation. Old owners without dispatch metadata must expire and obtain a new genuine owner; no in-place zero adoption.

Validation uses synthetic providers, real configured transport/factory seams and an isolated named Firestore emulator. It covers first purchase/restore, event custody/routing, ACK denial recovery, shared last-unit contention, atomic denial, callback/result loss, immutable single-use requests, late auth/final-read expiry, consent/retirement/owner fences, common and legacy corruption/rollback, strict parsers, closed construction and client-rule denial. Independent output/payment/privacy review is required; source/test acceptance does not authorize deployment or paid launch. General reconciliation pumping, financial feeds, broker entitlement publication, monthly credits, seven-day offline authority and deletion lifecycle remain separate work.
